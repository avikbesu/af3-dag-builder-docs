    Team Onboarding Guide¶

    What is airflow3-dag-gen?¶

    A single-source-of-truth DAG generator for Airflow 3. Your team writes one YAML file; the platform CI generates, validates, and packages the Python DAG files from it automatically.

    You never write raw Python DAG files. You write YAML, CI does the rest.

    1. Create your first project¶

    Create your project directory and a starter config:

    mkdir -p config/projects/<your-team>
touch config/projects/<your-team>/dags.yaml

    Open the file and set at minimum:

    version: "1.0"        # must match current schema version
name: <your-team>     # used as file prefix in generated output

dags:
  - id: <your-team>_my_first_dag
    schedule: "@daily"
    start_date: "2025-01-01"
    catchup: false
    tags: [<your-team>]
    default_args:
      owner: <your-team>
      retries: 1
      retry_delay_minutes: 5
      email_on_failure: false
    tasks:
      - id: hello
        operator: BashOperator
        params:
          bash_command: "echo 'Hello from <your-team>'"

    2. Validate locally before pushing¶

    # Check your YAML against the schema (catches typos, wrong types, missing fields)
pip install jsonschema pyyaml
python scripts/validate_configs.py

# Check for hardcoded secrets
python scripts/lint_secrets.py

# Check operator registry compliance
python scripts/validate_operators.py

    The same checks run automatically on every PR; fixing them locally saves a round-trip.

    3. Understand environment overrides¶

    Every field that should differ between dev, staging, and prod uses the _env key. Fields without _env apply to all environments.

    tasks:
  - id: run_job
    operator: BashOperator
    params:
      bash_command: "echo '[dev] light job'"   # used in dev by default
      _env:
        staging:
          bash_command: "echo '[staging] moderate job'"
        prod:
          bash_command: "/opt/scripts/heavy_job.sh"

    To disable a DAG or task in a specific environment:

    dags:
  - id: expensive_dag
    enabled:
      dev: true
      staging: false   # skipped entirely in staging
      prod: true

    4. Preview the resolved config (promotion helper)¶

    Before enabling a DAG in prod, see exactly what will change:

    python scripts/promote.py \
  --project <your-team> \
  --from staging \
  --to prod

    Output shows which DAGs change, which tasks are added/removed, and which parameters differ between the two environments.

    5. Use custom operators¶

    If you need an operator that is not in the standard list, you must:

    1. Register it — open a PR adding an entry to config/operators/registry.yaml:
    operators:
  - name: MySpecialOperator
    import_path: plugins.special.MySpecialOperator
    owner: <your-team>
    description: "Does the special thing"
    since: "1.0"
    1. Declare it in your project config:
    custom_operators:
  - name: MySpecialOperator
    import_path: plugins.special.MySpecialOperator
    1. Reference it in a task:
    tasks:
  - id: special_task
    operator: MySpecialOperator
    params:
      my_param: "value"

    The registry PR must be approved by the platform team (@platform-team).

    6. Avoid hardcoded secrets¶

    Do not put passwords, tokens, or connection strings directly in YAML:

    # BAD — gets flagged by lint_secrets.py and blocked in CI
params:
  password: "super_secret_123"
  db_url: "postgresql://user:pass@host/db"

    Do use Airflow Variables or Connections:

    # GOOD
params:
  bash_command: "DB_PASSWORD={{ var.value.my_db_password }} python run.py"

    7. Standard operators (no registration needed)¶

    These operators are built into the generators and can be used without any registration:

    Class name Provider
    BashOperator core
    PythonOperator core
    EmptyOperator core
    BranchPythonOperator core
    ShortCircuitOperator core
    TriggerDagRunOperator core
    HttpOperator apache-airflow-providers-http
    BigQueryInsertJobOperator apache-airflow-providers-google
    SparkSubmitOperator apache-airflow-providers-apache-spark
    KubernetesPodOperator apache-airflow-providers-cncf-kubernetes
    PostgresOperator apache-airflow-providers-postgres
    S3ToRedshiftOperator apache-airflow-providers-amazon

    8. What CI does on your PR¶

    Check What it validates
    Go Tests Generator unit tests pass
    Python Tests Adapter unit tests pass
    Lint Python Adapter and scripts code style
    Validate Config Schema Your YAML matches the JSON schema
    Validate Operator Registry All custom operators are registered
    Lint Secrets No hardcoded secrets in configs
    Backend Parity Test Both backends produce the same DAG IDs

    All checks must be green before a PR can be merged.

    9. Local generation (optional)¶

    To generate DAG files locally for inspection:

    # Install tools
make build

# Generate DAGs
make generate ENV=dev

# Generated files appear in output/dags/

    10. Who to contact¶

    • Platform team — schema changes, generator bugs, registry approvals, new standard operators
    • Your team lead — project-level DAG design questions

    Check config/operators/registry.yaml for operator ownership. Check .github/CODEOWNERS (when enabled) for file-level review routing.
