    Contributing Guide¶

    This guide is for developers working on the generator itself — the Go generator, DAG template, JSON schema, and test suites. For the guide on defining DAGs as a user, see docs/userguide/ (or the published MkDocs site).

    2. Development prerequisites¶

    Tool Version Purpose
    Go 1.22+ Build and test the generator
    Python 3.10+ Validation scripts, syntax checks
    Docker + Compose any recent Local Airflow smoke tests, image output mode
    golangci-lint 1.57+ Go linting (make lint)

    Install Python tools used by scripts:

    pip install jsonschema pyyaml

    3. Building locally¶

    # Build Go binary
make build

# same
make build-go
# Binary written to: app/dagGen/bin/daggen

# Install the git pre-commit hook (runs tests before every commit)
make install-hooks

    The pre-commit hook blocks commits that break any test. Bypass sparingly with git commit --no-verify.

    4. Running tests¶

    make test      # Go unit tests
make test-go   # same

    Test layout:

    Test file Coverage
    cmd/daggen/*_test.go CLI flags, binary integration
    internal/config/*_test.go YAML loading, project discovery, merging
    internal/env/*_test.go Environment resolution logic
    internal/generator/*_test.go Template rendering, operator resolution
    internal/generator/manifest_test.go Manifest struct correctness, env filtering
    internal/linter/*_test.go Rule matching, pattern validation, tag/description checks
    internal/output/*_test.go File writing, py_compile validation

    5. Architecture deep-dive¶

    5.1 Go generator pipeline¶

    main.go
  │
  ├── config/loader.go
  │     LoadSettings()        ← config/settings.yaml  (+ environments block)
  │     LoadLintRules()       ← config/linting.yaml   (optional)
  │     DiscoverProjects()    ← config/projects/*/
  │     LoadProject()         ← dags.yaml / defaults.yaml + extra *.yaml files
  │                              expandDAGInstances()  ← dag_instances → DAG structs
  │
  ├── env/resolver.go
  │     Resolve()             ← filters by enabled_envs, enabled_classes, enabled map
  │     resolveDAGFields()    ← DAG-level _env overrides (schedule, catchup, etc.)
  │     ResolveTasks()        ← filters disabled tasks, cleans dep edges
  │     resolveDefaultArgs()  ← merges _env overrides into default_args
  │     MergeParams()         ← merges _env overrides into task params
  │
  ├── linter/linter.go
  │     Lint()                ← checks dag_id/task_id patterns, required tags, description
  │
  ├── generator/dag.go
  │     Generate()            ← Phase 1: render all DAGs (serial)
  │                              Phase 2: write via goroutine pool (parallel py_compile)
  │     renderDAG()           ← builds DAGRenderData, executes template
  │     buildTaskRenderData() ← builds TaskRenderData slice
  │     collectCallbackImports() ← resolves callback import statements
  │
  ├── generator/manifest.go
  │     BuildManifest()       ← resolves env + builds Manifest struct → manifest.json
  │
  ├── generator/operator.go
  │     ResolveImports()      ← deduped import statements for all operators
  │     ResolveClass()        ← class name for template (last path segment)
  │
  ├── generator/template.go
  │     TemplateFuncs()       ← pythonBool, pythonValue, pyStr, etc.
  │
  ├── templates/dag.py.tmpl   ← Go text/template → Python source
  │
  └── output/local.go | output/image.go
        Write()               ← writes .py, validates with py_compile (parallel)
        Flush()               ← saves incremental hash cache (.daggen-cache.json)

    Key design choice: the template receives DAGRenderData — a plain Go struct with no methods. All logic lives in Go; the template is pure presentation. This keeps the template readable and keeps business logic testable.

    5.2 Environment resolution¶

    Resolution happens after preprocessing (defaults → task library → templates) and before rendering. The key invariant: the resolved struct contains no _env keys and no disabled items.

    Input DAG (raw from YAML)
  │
  ├── dag.enabled_envs set and env not in list?     →  skip entirely (return false)
  │
  ├── dag.enabled_classes set and envClass not in list?  →  skip entirely (return false)
  │
  ├── dag.enabled[env] == false?  →  skip entirely (return false)
  │
  ├── resolveDAGFields(dag, env)
  │     apply _env[env] overrides: schedule, catchup, max_active_runs, tags
  │
  ├── resolveDefaultArgs(dag.DefaultArgs, env)
  │     merge _env[env] fields into base, nil out EnvOverrides
  │
  └── ResolveTasks(dag.Tasks, env)
        for each task:
          isEnabled(task.Enabled, env) == false?  →  add to disabled set
        for each non-disabled task:
          MergeParams(task.Params, env)           →  merge _env, remove _env key
          filterDeps(task.Dependencies, disabled) →  remove edges to disabled tasks
          task.Enabled = nil

    Go: app/dagGen/internal/env/resolver.go

    5.3 Template rendering¶

    The DAG template (app/dagGen/templates/dag.py.tmpl) is a standard Go text/template. It is embedded via go:embed in templates/embed.go and read at runtime.

    Key template conventions: - {{- action }} trims all whitespace/newlines before the action - {{ action -}} trims all whitespace/newlines after the action - Optional fields use {{- if .Field }}...{{- end }} — omitted when zero value - *bool fields use the boolPtrRendered helper (returns "" for nil → skipped by {{with}}) - All string-to-Python conversions go through pyStr (quoted) or pythonValue (type-aware)

    6. Making changes¶

    6.1 Adding a new YAML field¶

    Changes must be made in all four places — schema, types, resolver (if env-overridable), generator, and template.

    Example: adding retries_exponential_backoff: bool to tasks.

    1. JSON Schema (config/schema/dags.schema.json) — add to the task definition:

    "retries_exponential_backoff": {
  "type": "boolean",
  "description": "Use exponential backoff between retries instead of fixed delay"
}

    2. Go types (app/dagGen/internal/config/types.go) — add to Task:

    RetriesExponentialBackoff bool `yaml:"retries_exponential_backoff,omitempty"`

    3. Render data (app/dagGen/internal/generator/dag.go) — add to TaskRenderData:

    RetriesExponentialBackoff bool

    Populate it in buildTaskRenderData():

    result[i] = TaskRenderData{
    ...
    RetriesExponentialBackoff: t.RetriesExponentialBackoff,
}

    4. Template (app/dagGen/templates/dag.py.tmpl) — add inside the Operator(...) constructor:

    {{- if .RetriesExponentialBackoff }}
        retries_exponential_backoff=True,
{{- end }}

    5. Tests — add a Go test in dag_test.go.

    6.2 Adding a standard operator¶

    Standard operators are registered in the Go generator (app/dagGen/internal/generator/operator.go):

    var standardOperators = map[string]string{
    ...
    "S3KeySensor": "from airflow.providers.amazon.aws.sensors.s3 import S3KeySensor",
}

    Update the standard operator table in docs/userguide/custom-operators.md and docs/onboarding.md.

    6.3 Modifying the DAG template¶

    The template is at app/dagGen/templates/dag.py.tmpl. It is embedded at compile time — no separate copy step needed.

    Whitespace control is critical in Python output. Use {{- and -}} to eliminate unintended blank lines. Run make generate && python3 -m py_compile output/dags/*.py after any template change.

    Testing template output — write a table-driven test in dag_test.go that creates a minimal config.DAG, calls renderDAG, and asserts on specific substrings in the output:

    func TestMyNewField(t *testing.T) {
    dag := config.DAG{
        ID: "test_dag", Schedule: "@daily", StartDate: "2024-01-01",
        MyNewField: "expected_value",
        Tasks: []config.Task{{ID: "t1", Operator: "EmptyOperator"}},
    }
    project := &config.ProjectConfig{Name: "proj", DAGs: []config.DAG{dag}}
    settings := &config.Settings{Environment: "dev"}

    var w mockOutputHandler
    if err := Generate([]*config.ProjectConfig{project}, settings, &w); err != nil {
        t.Fatal(err)
    }
    if !strings.Contains(w.files["test_dag"], "expected_value") {
        t.Errorf("expected 'expected_value' in output:\n%s", w.files["test_dag"])
    }
}

    6.4 Extending environment resolution¶

    When adding a new field that should be env-overridable (like an existing _env field):

    Go — add to DefaultArgsOverride (for default_args fields) or handle in MergeParams (for task params, which already handles any key generically).

    For a completely new override section, follow the pattern in resolveDefaultArgs:

    func resolveDefaultArgs(da config.DefaultArgs, env string) config.DefaultArgs {
    ...
    if ov.MyNewField != nil {
        da.MyNewField = *ov.MyNewField
    }
    ...
}

    Task-level params already use generic map merging (MergeParams) so no changes are needed there for new task param fields.

    6.5 Adding a template function¶

    Template functions live in app/dagGen/internal/generator/template.go. Register them in TemplateFuncs():

    func TemplateFuncs() template.FuncMap {
    return template.FuncMap{
        ...
        "myNewFunc": myNewFunc,
    }
}

func myNewFunc(input string) string {
    return strings.ToUpper(input)
}

    Then use in the template: {{ .MyField | myNewFunc }}

    Write a unit test alongside the function. Keep functions pure and side-effect-free.

    6.6 Adding a linting rule¶

    Linting rules are pure data — no code change needed for most additions. Edit config/linting.yaml:

    rules:
  dag_id:
    pattern: "^[a-z][a-z0-9_]*$"
    message: "DAG IDs must be lowercase snake_case"
  required_tags:
    - team
    - domain
  description_required: true

    To add a new rule type (e.g. check that schedule matches a pattern):

    1. Add a field to LintRuleSet in app/dagGen/internal/config/linting.go
    2. Add a field to LintRules.Rules if needed
    3. Add the check in Lint() in app/dagGen/internal/linter/linter.go
    4. Add a test in linter_test.go

    The linter is always bypassed when config/linting.yaml does not exist.

    7. Writing tests¶

    Go tests¶

    Follow the existing table-driven pattern. Use mockOutputHandler from dag_test.go to capture output without writing files:

    type mockOutputHandler struct {
    files map[string]string
}
func (m *mockOutputHandler) Write(dagID, group, content string) error {
    if m.files == nil { m.files = make(map[string]string) }
    m.files[dagID] = content
    return nil
}

    Test naming: Test<Package>_<Scenario> — e.g., TestResolver_DisabledTaskDepsRemoved, TestGenerate_TriggerRuleRendered.

    Coverage requirements: - Every new field added to types.go needs at least one renderer test in dag_test.go - Every change to resolver.go needs a resolution test in resolver_test.go - Operator resolution changes need tests in operator_test.go

    8. Code style and linting¶

    make lint       # runs golangci-lint

    Go: - Standard gofmt formatting (enforced by golangci-lint) - No panic in library code — return errors - Error messages: lowercase, no trailing punctuation - Use fmt.Errorf("context: %w", err) for error wrapping

    Comments: - Write comments only when the why is non-obvious - No doc comments restating what the function name already says - Mark intentional design constraints with a short inline comment

    9. Schema versioning¶

    The schema version ("1.0") is validated in app/dagGen/internal/config/loader.go:

    const CurrentSchemaVersion = "1.0"

    When to bump the version:

    Change type Action
    New optional field No bump — backwards compatible
    Removed field Bump to "2.0"
    Renamed field Bump to "2.0"
    Changed field type Bump to "2.0"
    New required field Bump to "2.0"

    When bumping: 1. Change CurrentSchemaVersion in loader.go 2. Update the version pattern in dags.schema.json if needed 3. Update all version: "1.0" lines in config/projects/ 4. Add a migration note in this file

    10. Keeping docs/userguide/ current¶

    Field reference tables in docs/userguide/yaml-reference.md and docs/userguide/custom-operators.md are auto-generated from the JSON schema and operator.go. Never edit them by hand — your changes will be overwritten on the next make docs run.

    When you add or change a field:

    # 1. Update the schema (add/edit the property + its description)
#    config/schema/dags.schema.json

# 2. Regenerate the guide
make docs

# 3. Commit both files together
git add config/schema/dags.schema.json docs/userguide/yaml-reference.md

    Sections generated automatically (marked with <!-- generated:X --> / <!-- /generated:X -->): - DAG fields table (docs/userguide/yaml-reference.md) — from schema.definitions.dag - Task fields table (docs/userguide/yaml-reference.md) — from schema.definitions.task - trigger_rule values table (docs/userguide/yaml-reference.md) — from schema.definitions.task.properties.trigger_rule.enum - default_args fields table (docs/userguide/yaml-reference.md) — from schema.definitions.default_args - Standard operators table (docs/userguide/custom-operators.md) — from app/dagGen/internal/generator/operator.go

    Sections maintained by hand (everything else — narrative, examples, FAQ, headings).

    CI gate: make check runs python scripts/generate_docs.py --check and fails if the guide is stale. You will see a unified diff showing exactly what changed in the schema but was not regenerated into the guide.

    Adding per-value descriptions to trigger_rule or weight_rule: these are stored in the TRIGGER_RULE_DESCRIPTIONS dict in scripts/generate_docs.py (JSON Schema draft-7 has no per-enum-value metadata). Update the dict there.

    11. Pull request checklist¶

    Before opening a PR, confirm:

    • [ ] make test passes (Go unit tests)
    • [ ] make lint passes (no golangci-lint errors)
    • [ ] make validate passes against the existing project configs
    • [ ] New fields are added to all relevant locations: schema, Go types, Go renderer, Go template
    • [ ] New fields have tests in dag_test.go
    • [ ] docs/userguide/ is updated with any new user-facing fields or behaviours
    • [ ] Standard operator additions are documented in the operator table in docs/userguide/custom-operators.md and docs/onboarding.md
    • [ ] No hardcoded secrets, no debug print statements
    • [ ] Commit messages are clear and self-contained — no "AI-generated", "Claude", or tool attribution
    • [ ] make lint-dags passes (or no config/linting.yaml present)
    • [ ] make check passes (schema + operators + secrets + linting + docs)
    • [ ] New linting rules added to config/linting.yaml are documented in docs/userguide/validation-ci.md
    • [ ] make validate output shows correct env class for the test environment

    11. Project decisions and trade-offs¶

    Why Go for the generator?

    Fast binary, zero Python runtime dependency, straightforward text/template for code generation, easy to embed templates at compile time with go:embed.

    Why Go text/template and not a proper AST?

    The generated Python is simple and fixed in structure. Template-based generation is easier to read, modify, and review than AST manipulation. The trade-off is that whitespace control requires {{- / -}} discipline.

    Why not support sensor operators as standard?

    Sensor configuration is highly operator-specific (poke interval, timeout, mode). Rather than guessing a lowest-common-denominator API for each sensor type, we keep the standard list focused on common action operators and let teams register the exact sensor class they need via custom_operators.

    Why is _env a shallow merge?

    Deep merging nested objects creates unexpected results when a user wants to replace a nested config entirely. Shallow merge is predictable: the entire value is replaced, not patched. For granular overrides, structure your YAML with scalar values that each have their own _env.

    Why is there no circular dependency detection?

    Adding a graph cycle check at generation time adds complexity but catches a problem that Airflow's own parser already catches at import time with a clear error message. Given that syntax validation (py_compile) already runs after generation, the cycle would be caught before deployment on the very next make generate.

    Why is task library expansion non-recursive?

    Recursive expansion (library tasks that use other library tasks) creates hard-to-trace resolution chains. The explicit design forces library entries to be self-contained, making their behaviour predictable at the use-site.

    Why is parallel generation opt-in at the output handler level (not a CLI flag)?

    The Generate() function checks whether the OutputHandler implements Concurrent() bool rather than accepting a --workers flag. This keeps the generator and output packages decoupled. LocalWriter returns true (safe because each goroutine writes a different file). StdoutWriter returns false (serial to keep dry-run output readable and deterministic).

    Why is the incremental cache keyed by dag_id rather than input YAML hash?

    Keying on the rendered output hash (not the input) means any change that affects the generated Python — template changes, Go binary updates, environment name changes — automatically invalidates the cache. Input-keyed caches would silently skip files after template or generator logic changes.

    Why is the linter a separate package rather than part of the validator?

    The validator (config/loader.go) enforces structural correctness (required fields, valid types). The linter enforces project conventions (naming patterns, required tags). Separating them makes the linter independently testable and entirely optional — teams can use the generator without ever touching linting.yaml.
