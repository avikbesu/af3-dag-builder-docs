    Validation, Output & CI¶

    daggen CLI flags¶

    make generate, make validate, etc. are thin wrappers around the daggen binary. All flags are optional and can be combined:

    Flag Purpose
    --settings <path> Path to settings.yaml (default config/settings.yaml)
    --env <name> Override the environment from settings.yaml for this run only
    --project <name> Generate/validate only the named project instead of every project under config/projects/
    --validate Check configs and print a report; writes nothing
    --dry-run Render DAGs and print the Python source to stdout instead of writing files
    --incremental Skip DAGs unchanged since the last run (see Incremental generation)
    --manifest Write manifest.json after generation (see DAG manifest)
    --output-dir <path> Override the output directory from settings.yaml (useful in CI)
    --base-dir <path> Repository root used for auto-discovering config/projects/ (default .)

    Use case — inspect one DAG's generated Python without writing any files:

    app/dagGen/bin/daggen --settings config/settings.yaml --project my_team --dry-run

    This is the fastest way to check "what will this actually render to?" while iterating on a template or a tricky _env override, without touching output/dags/ or running a full make generate.

    Use case — validate or generate a single project in a large monorepo:

    app/dagGen/bin/daggen --settings config/settings.yaml --project ecommerce_platform --validate

    Output modes¶

    Local (default)¶

    Generated .py files are written to the filesystem:

    # config/settings.yaml
output:
  mode: local
  local:
    path: ./output/dags

    make generate ENV=prod
ls output/dags/

    Docker image¶

    Generated files are baked into a Docker image based on the Airflow base image:

    output:
  mode: image
  image:
    name: airflow-dags
    tag: "1.0.0"
    base_image: apache/airflow:3.2.2
    push: true
    registry: myregistry.example.com

    make generate ENV=prod
# Builds and optionally pushes: myregistry.example.com/airflow-dags:1.0.0

    Plugins are bundled automatically

    If config/plugins/ exists and is non-empty, it's copied into the build context and COPY'd to /opt/airflow/plugins/ alongside the DAGs — no extra config needed. The Generate and Package DAGs CI workflow does the same for the local-mode artifact zip: generated DAGs land under dags/ and, when present, plugins land under plugins/, so the artifact is deployable as-is.

    Validation and linting¶

    Run all validators locally before pushing:

    make validate

    This runs three checks:

    Check Command What it catches
    Schema validation python scripts/validate_configs.py Wrong field types, missing required fields, invalid patterns
    Operator registry python scripts/validate_operators.py Custom operators used in configs but not registered in registry.yaml
    Secret detection python scripts/lint_secrets.py Hardcoded passwords, tokens, connection strings

    Note

    All three checks (and scripts/promote.py) validate every *.yaml file in a project directory — the same merged view the Go generator uses for multi-file projects — not just dags.yaml or defaults.yaml.

    Do not hardcode secrets in YAML:

    # BAD — flagged and blocked in CI
params:
  password: "hunter2"
  db_url: "postgresql://user:pass@host/db"

# GOOD — use Airflow Variables or Connections
params:
  bash_command: "DB_PASS={{ var.value.my_db_password }} python run.py"

    Generator-level safety checks¶

    Beyond JSON schema validation, the Go generator itself (daggen, run by make generate / make validate) rejects configs that would otherwise fail silently or unsafely at Airflow parse time:

    Check Rejects
    DAG/task id character allowlist Any id not matching ^[a-zA-Z0-9_]+$ — ids are emitted as bare Python identifiers, so this also closes a code-injection gap if daggen is ever run without the separate validate-schema step
    group path safety group segments that don't match ^[a-zA-Z0-9_-]+$ (blocks path-traversal values like ../../etc that would otherwise be joined into the output file path)
    Duplicate task ids Two tasks with the same id inside one DAG
    Dangling / self dependencies A task's dependencies entry that doesn't match any task id in the same DAG, or a task depending on itself
    Duplicate collection ids Two entries with the same id in custom_operators, task_library, or dag_templates
    output.image.base_image newline injection A base_image value containing a newline (would otherwise inject arbitrary Dockerfile instructions)
    Malformed dates start_date / end_date values that aren't valid calendar dates (e.g. 2024-13-45) even if they match the YYYY-MM-DD shape

    Note

    These run as part of make validate and make generate — you don't need a separate command. They catch mistakes that used to only surface as an Airflow DAG-parse error or, in the id/path cases, as a security gap.

    Naming convention linting¶

    If config/linting.yaml exists, the generator checks DAG IDs, task IDs, tags, and descriptions against the rules you define. Violations cause --validate and make lint-dags to exit with a non-zero status.

    config/linting.yaml example:

    rules:
  dag_id:
    pattern: "^[a-z][a-z0-9_]*$"
    message: "DAG IDs must be lowercase snake_case"
  task_id:
    pattern: "^[a-z][a-z0-9_]*$"
    message: "Task IDs must be lowercase snake_case"
  required_tags:
    - team
  description_required: true

    Supported rules:

    Rule key Type Description
    dag_id.pattern regex string DAG IDs that don't match exit 1
    task_id.pattern regex string Task IDs that don't match exit 1
    required_tags list of string Every DAG must carry all listed tags
    description_required boolean Every DAG must have a non-empty description

    Note

    Linting is entirely opt-in — delete or rename linting.yaml to disable it. The make check target runs make lint-dags as part of the full CI gate.

    make lint-dags    # validate + linting only
make check        # schema + operators + secrets + linting + docs

    Incremental generation¶

    Pass --incremental to skip regenerating DAGs whose content hasn't changed since the last run. The generator writes a .daggen-cache.json hash file to the output directory and compares SHA-256 hashes on subsequent runs.

    # First run — generates all DAGs and writes cache
daggen --settings config/settings.yaml --incremental

# Second run — unchanged DAGs are skipped (shown as "↩ … (unchanged)")
daggen --settings config/settings.yaml --incremental

    When to use it:

    Scenario Benefit
    Large repo (500+ DAGs) in CI Skip py_compile for unchanged files; typical CI re-run goes from 30s → 3s
    Local iteration on one project Only re-generates the project you edited
    Post-merge sync Unchanged DAGs stay in place; only changed projects regenerate

    The cache is keyed by dag_id. Changing the environment name or any YAML that affects the rendered output will cause a regeneration. Delete .daggen-cache.json to force a full regeneration.

    DAG manifest¶

    Pass --manifest to write a manifest.json file alongside the generated .py files. The manifest lists every DAG that was generated for the active environment.

    make generate ENV=prod
daggen --settings config/settings.yaml --manifest
# → output/dags/manifest.json

    manifest.json structure:

    {
  "generated_at": "2025-06-17T12:00:00Z",
  "environment": "prod",
  "env_class": "production",
  "solution": "custom",
  "git_commit": "a1b2c3d",
  "dag_count": 42,
  "dags": [
    {
      "id": "my_dag",
      "project": "my_project",
      "file": "my_dag.py",
      "group": "",
      "schedule": "@daily",
      "start_date": "2025-01-01",
      "catchup": false,
      "max_active_runs": 1,
      "tags": ["team_a", "prod"],
      "task_count": 5
    }
  ]
}

    Use cases:

    • Feed a governance dashboard with the active DAG inventory per environment
    • Diff manifests across environments to see what runs where
    • Use dag_count in CI as a sanity check (alert if it drops unexpectedly)
    • Drive operator/tag coverage reports
