    Environments¶

    Environment overrides¶

    Any scalar field under params or default_args can be overridden per environment using the _env key. The base value is the fallback for environments not explicitly listed.

    tasks:
  - id: run_job
    operator: BashOperator
    params:
      bash_command: "echo dev run"      # used in dev (and any unlisted env)
      workers: 1
      _env:
        staging:
          bash_command: "echo staging run"
          workers: 4
        prod:
          bash_command: "/opt/scripts/prod_run.sh"
          workers: 16

    Effective params after resolution, per environment:

    bash_command: "echo dev run"
workers: 1

    bash_command: "echo staging run"
workers: 4

    bash_command: "/opt/scripts/prod_run.sh"
workers: 16

    Enable/disable a DAG per environment:

    dags:
  - id: expensive_dag
    enabled:
      dev: true
      staging: false    # skipped in staging; not generated at all
      prod: true

    Enable/disable a task per environment:

    tasks:
  - id: debug_task
    operator: BashOperator
    enabled:
      dev: true
      staging: false
      prod: false       # task removed; its dependents' upstream edges are cleaned up
    params:
      bash_command: "echo debug"

    Full resolution order (this is the complete picture — it's what actually runs, in order, for every DAG on every generation):

    %%{init: {"look": "handDrawn"}}%%
flowchart TD
    A["DAG"] --> B{"enabled_envs set\nand env not listed?"}
    B -->|yes| X["DAG excluded\n(not generated at all)"]
    B -->|no| Y{"enabled_clusters set\nand cluster not listed?"}
    Y -->|yes| X
    Y -->|no| C{"enabled_classes set\nand class not listed?"}
    C -->|yes| X
    C -->|no| D{"enabled[env] == false?"}
    D -->|yes| X
    D -->|no / unset| E["Merge default_args._env[env]"]
    E --> F["Merge DAG-level _env[env]\nschedule, catchup, max_active_runs, tags"]
    F --> G["Per task: drop if enabled[env]==false,\nclean dangling dependency edges,\nmerge params._env[env]"]
    G --> I["Per task: merge task-level _env[env]\ntrigger_rule, pool, pool_slots, queue,\npriority_weight, weight_rule,\nexecution_timeout_minutes, sla_minutes"]
    I --> H["Resolved DAG -> rendered to output/dags/*.py"]

    The three whitelists (steps B/Y/C above — enabled_envs, enabled_clusters, enabled_classes) are covered in detail in enabled_envs, enabled_clusters, and enabled_classes below; the merge steps (E/F/G/I) are covered in DAG-level _env overrides and Task-level _env overrides.

    Environment taxonomy and classes¶

    By default the generator recognises three built-in environment names and maps them to a class:

    Environment name(s) Class
    prod, prd, production production
    staging, stg staging
    anything else (e.g. dev, qa) non-production

    You can replace this with an explicit taxonomy in config/settings.yaml:

    solution: custom
environment: prd-eu

environments:
  prd-eu:
    label: "Production EU"
    class: production
  prd-us:
    label: "Production US"
    class: production
  stg:
    label: "Staging"
    class: staging
  dev:
    label: "Development"
    class: non-production

    Note

    Once defined, the class is used by enabled_classes filtering and shown in make validate output.

    Clusters: grouping environments by Airflow deployment¶

    Class groups environments by safety semantics (production vs. staging vs. non-production). Separately, environments entries can declare a cluster, which groups environments by deployment topology — which physical/logical Airflow cluster they run on. Multiple environment names can share one cluster:

    solution: custom
environment: demo

environments:
  dev:
    label: "Development"
    class: non-production
    cluster: dev
  demo:
    label: "Demo"
    class: non-production
    cluster: dev
  stg:
    label: "Staging"
    class: staging
    cluster: stg
  preprd:
    label: "Pre-production"
    class: staging
    cluster: stg
  prd:
    label: "Production"
    class: production
    cluster: prd

    Here the dev cluster hosts both the dev and demo environments, the stg cluster hosts stg and preprd, and prd is its own single-environment cluster.

    cluster is optional per environment entry; when omitted (or when no environments block is declared at all), EnvCluster() returns "" and enabled_clusters whitelists are simply never satisfied by name — there is no built-in cluster-name inference the way there is for class.

    Note

    Once defined, the cluster is used by enabled_clusters filtering and shown in make validate output.

    Walkthrough: add a new custom cluster with multiple environments¶

    Say you're standing up a brand-new Airflow instance, qa-cluster, that will host three virtual environments: qa1, qa2, and qa3.

    Step 1 — declare the cluster and its environments in config/settings.yaml:

    solution: custom
environment: qa1          # the environment this generation run targets

environments:
  qa1:
    label: "QA 1"
    class: non-production
    cluster: qa-cluster
  qa2:
    label: "QA 2"
    class: non-production
    cluster: qa-cluster
  qa3:
    label: "QA 3"
    class: non-production
    cluster: qa-cluster
  # ...your existing dev/stg/prd entries stay as they are

    All three envs share cluster: qa-cluster, so anything scoped to that cluster runs identically across qa1, qa2, and qa3 — but each keeps its own env name for _env overrides, enabled: {} maps, etc.

    Step 2a — a DAG that should run on every env in this cluster (any of qa1/qa2/qa3, but nowhere else):

    dags:
  - id: qa_cluster_smoke_test
    schedule: "@daily"
    start_date: "2025-01-01"
    catchup: false
    enabled_clusters: [qa-cluster]   # runs whenever the active env's cluster is qa-cluster
    default_args:
      owner: platform
      retries: 1
      retry_delay_minutes: 5
    tasks:
      - id: ping
        operator: BashOperator
        params:
          bash_command: "echo qa-cluster smoke test"

    Step 2b — a DAG scoped to only one specific env in that cluster (e.g. qa2 only, not qa1 or qa3):

    dags:
  - id: qa2_only_experiment
    schedule: "@daily"
    start_date: "2025-01-01"
    catchup: false
    enabled_envs: [qa2]              # runs only when the active env is exactly qa2
    default_args:
      owner: platform
      retries: 1
      retry_delay_minutes: 5
    tasks:
      - id: run
        operator: BashOperator
        params:
          bash_command: "echo qa2-only run"

    Step 3 — generate and confirm. The generator always targets one active environment per run (whichever environment: in settings.yaml points to, or --env/ENV= override). Run it once per environment you need output for:

    make validate ENV=qa1   # confirm which DAGs would generate for qa1
make generate ENV=qa1   # qa_cluster_smoke_test: enabled | qa2_only_experiment: skipped

make validate ENV=qa2
make generate ENV=qa2   # qa_cluster_smoke_test: enabled | qa2_only_experiment: enabled

make validate ENV=qa3
make generate ENV=qa3   # qa_cluster_smoke_test: enabled | qa2_only_experiment: skipped

    make validate prints cluster=qa-cluster in its Settings valid: ... line and lists each DAG as [enabled]/[disabled], so you can confirm the scoping before generating.

    DAG-level _env overrides¶

    In addition to params._env and default_args._env, you can override DAG-level scheduling fields per environment using _env at the DAG level:

    dags:
  - id: heavy_pipeline
    schedule: "@daily"
    catchup: false
    max_active_runs: 1
    tags: [team_a]

    _env:
      prod:
        schedule: "0 3 * * *"    # tighter cron in prod
        max_active_runs: 2        # allow more concurrency in prod
      staging:
        tags: [team_a, staging]   # add extra tag in staging

    Fields supported in a DAG-level _env block:

    Field Description
    schedule Override the cron / preset schedule
    catchup Override the catchup flag
    max_active_runs Override the maximum concurrent runs
    tags Replace the entire tags list

    Note

    Only non-null values in the override block are applied; unset fields keep their base value.

    Task-level _env overrides¶

    In addition to params._env (arbitrary operator params) and the DAG-level _env block (schedule/catchup/max_active_runs/tags), a task's scheduling and execution fields can be overridden per environment using _env at the task level:

    tasks:
  - id: heavy_transform
    operator: PythonOperator
    pool: default_pool
    priority_weight: 1
    execution_timeout_minutes: 30
    params:
      python_callable: pkg.transform

    _env:
      prod:
        pool: high_mem            # run on a dedicated pool in prod
        priority_weight: 10        # prioritize in prod
        execution_timeout_minutes: 120   # allow longer runtime in prod
        queue: prod_queue

    Fields supported in a task-level _env block:

    Field Description
    trigger_rule Override how this task reacts to upstream task state
    pool Override the Airflow pool this task runs in
    pool_slots Override the number of pool slots this task occupies
    queue Override the Celery/Kubernetes queue
    priority_weight Override the task's priority
    weight_rule Override the priority-weighting algorithm
    execution_timeout_minutes Override the maximum runtime before the task is killed
    sla_minutes Override the expected maximum duration before on_sla_miss_callback fires

    Note

    Only non-null values in the override block are applied; unset fields keep their base value. For overriding operator-specific params (e.g. bash_command, connection ids), use params._env instead — see Environment overrides above.

    enabled_envs, enabled_clusters, and enabled_classes¶

    Three whitelist fields give you precise control over which environments a DAG is generated for, without maintaining a per-env enabled map.

    enabled_envs — list of environment names:

    dags:
  - id: mock_data_loader
    schedule: "@hourly"
    enabled_envs: [dev, qa]   # only generated in dev and qa; skipped in staging and prod
    ...

    enabled_clusters — list of Airflow clusters (as declared in settings.yaml's environments block):

    dags:
  - id: cluster_scoped_dag
    schedule: "@daily"
    enabled_clusters: [dev]   # generated whenever the active env's cluster is "dev" (e.g. both dev and demo)
    ...

    enabled_classes — list of environment classes:

    dags:
  - id: integration_test_dag
    schedule: "@daily"
    enabled_classes: [non-production]   # generated in dev and staging; never in prod
    ...

    Comparison:

    Mechanism Key question Example use case
    enabled: {prod: false} Is this specific env explicitly disabled? One-off exclusion
    enabled_envs: [dev] Is the active env in this whitelist? Dev-only tooling
    enabled_clusters: [dev] Does the active env's cluster match? All envs deployed to the same Airflow cluster (e.g. dev + demo)
    enabled_classes: [non-production] Does the active env's class match? All non-prod envs regardless of name

    Note

    All four mechanisms must pass for the DAG to be generated — see the Full resolution order diagram above for the exact check order.

    Previewing and applying environment diffs¶

    Before promoting a DAG from staging to prod, check exactly what will change:

    python scripts/promote.py \
  --project my_team \
  --from staging \
  --to prod

    Output shows which DAGs change, which tasks are added/removed, and which parameters differ between the two environments.

    Generating an apply patch¶

    Once you've reviewed the diff and decided which changes to backfill, use --apply to generate the minimal _env.{to_env} YAML stanza:

    # Print to stdout
python scripts/promote.py --project my_team --from staging --to prod --apply

# Write to a file for review
python scripts/promote.py --project my_team --from staging --to prod --apply --output patch.yaml

    The output is a ready-to-paste YAML block. Copy the relevant sections into your dags.yaml, run make validate, then commit.

    # Makefile shortcut
make promote-apply PROJECT=my_team FROM=staging TO=prod

    Warning

    --apply shows field-level changes only. DAGs that are entirely enabled or disabled in one environment (but not the other) still require manual enabled configuration.
