    airflow3-dag-gen¶

    Generate Apache Airflow 3 DAGs from a single canonical YAML config using a Go-based generator.

    Requires Apache Airflow 3.2.2+. This project targets the Airflow 3.x SDK and provider package layout; it is not compatible with Airflow 2.x.

    Features¶

    • Single config — define DAGs once in config/projects/<project>/dags.yaml
    • Per-environment support — enable/disable DAGs and tasks per env (dev/staging/prod); override params and default_args per env with _env blocks
    • Multi-project — one repo holds configs for many Airflow projects, each in its own sub-directory
    • Airflow 3 Assets (3.0+) — declare Asset outlets and inlets on any task; enables data-aware DAG scheduling
    • Dynamic task mapping (3.0+) — .partial().expand() and .partial().expand_kwargs() generated from YAML; map_index_template supported
    • DAG display name (3.2+) — set a human-readable display name independent of the DAG ID via dag_display_name
    • Standard provider paths (3.0+) — generated imports use airflow.providers.standard.* and airflow.sdk; no legacy airflow.operators.* paths
    • Flexible output — copy DAGs to a local directory or bake them into a Docker image
    • Syntax validation — every generated .py file is validated with python3 -m py_compile before reporting success
    • Makefile — all developer actions via make
    • Environment taxonomy — define named environments with an optional class (production, staging, non-production) in settings.yaml; built-in defaults for prd/prod/stg/staging/dev
    • Airflow cluster grouping — group environments under a cluster in settings.yaml (e.g. a dev cluster hosting both dev and demo, a stg cluster hosting stg and preprd) to model deployment topology independently of the prod-safety class
    • Fine-grained env scoping — enabled_envs whitelist (DAG only generated for these named environments), enabled_clusters whitelist (DAG only generated when the active env belongs to this cluster), and enabled_classes whitelist (DAG only generated when the active env belongs to this class); ideal for non-prod-only validation/mock DAGs
    • DAG-level _env overrides — override schedule, catchup, max_active_runs, or tags per environment at the DAG level (previously only params and default_args supported _env)
    • dag_instances list — stamp N DAGs from one template in a compact list; avoids repeating identical DAG blocks with template:
    • Parallel generation — goroutine worker pool for concurrent py_compile validation; ~8× faster at 1000+ DAG scale
    • Incremental generation — --incremental flag caches SHA-256 of each rendered file; unchanged DAGs are skipped in subsequent runs
    • DAG manifest — --manifest flag writes manifest.json to the output directory listing every generated DAG with its metadata
    • Naming convention linter — config/linting.yaml defines regex rules for DAG/task IDs, required tags, and description presence; make lint-dags and make check enforce them in CI
    • Promote --apply — promote.py --apply prints (or --output FILE writes) the minimal _env.{to_env} YAML patch to make two environments converge

    Why af3-dag-builder over Astro DAG Factory?¶

    Astro DAG Factory lets you define Airflow DAGs in YAML — but it works by loading and evaluating that YAML inside the Airflow scheduler at parse time. Every scheduler heartbeat re-parses your YAML files and rebuilds DAG objects in memory. af3-dag-builder takes the opposite approach: it is a compile-time code generator that produces static Python .py files you review, commit, and deploy like any other code.

    af3-dag-builder Astro DAG Factory
    How it works Go binary generates static .py files Python library builds DAGs in-memory at parse time
    Airflow 3 native Built for Airflow 3 from the ground up Built for Airflow 2; Airflow 3 support is incomplete
    Scheduler overhead None — DAGs are already Python files YAML parsed on every scheduler scan cycle
    Reviewable output Real .py files in git, diffable and auditable No generated files; DAG code is never visible
    Syntax validation python3 -m py_compile on every file before deploy No pre-deployment validation
    Multi-environment First-class _env overrides; per-env enable/disable No built-in environment promotion model
    Secret detection Built-in lint_secrets.py blocks hardcoded secrets Not provided
    Operator governance Central registry.yaml; unknown operators fail CI No operator registry
    Dynamic task mapping Native .expand() / .expand_kwargs() support Not supported for Airflow 3
    Airflow 3 Assets Native Asset inlet/outlet declarations Not supported
    Reuse patterns DAG templates + task library Not provided
    Promotion diff scripts/promote.py shows staging→prod delta Not provided
    Parallel generation Worker pool; py_compile runs in parallel (~8× faster at scale) Python interpreter (serial)
    Incremental generation --incremental skips files with unchanged content hash Full regeneration every time
    DAG manifest --manifest → manifest.json with per-DAG metadata Not provided
    Naming convention linter config/linting.yaml with regex + tag rules; CI gate Not provided
    Promote --apply promote.py --apply prints _env patch to close env gap Not provided
    Non-prod-only DAGs enabled_classes: [non-production] limits DAG to dev/staging class Not provided
    Cluster-scoped DAGs enabled_clusters: [dev] limits DAG to all envs sharing an Airflow cluster Not provided
    Generator speed Compiled Go binary Python (interpreted at runtime)

    The core trade-off: DAG Factory is a lighter drop-in for existing Airflow 2 deployments — if you already run Python DAGs and want a quick YAML abstraction, it works. af3-dag-builder is the right choice when you want Airflow 3 semantics, CI-gated validation, environment promotion discipline, and generated files that your team can read, review, and audit exactly like handwritten code.

    Quick Start¶

    # 1. Build the Go generator
make build-go

# 2. Validate your config
make validate

# 3. Generate DAGs (dev environment, local output)
make generate

# 4. Inspect output
ls output/dags/

# 5. Smoke-test with local Airflow 3
make airflow-up
# → http://localhost:8080  (admin / admin)
make airflow-down

    docker-compose.yml ships a placeholder AIRFLOW_JWT_SECRET default for local use only. To override it, copy .env.example to .env (gitignored) and set a real value — never commit actual secrets.

    Project Layout¶

    airflow3-dag-gen/
├── app/dagGen/          # Go DAG generator
├── config/
│   ├── settings.yaml    # Runtime settings (solution, env, output mode)
│   ├── linting.yaml     # Optional naming-convention rules (DAG/task IDs, required tags)
│   └── projects/
│       ├── project_a/dags.yaml
│       └── project_b/dags.yaml
├── scripts/
│   └── pre-commit       # Git pre-commit hook (install: make install-hooks)
├── output/dags/         # Generated .py files (gitignored)
├── docker-compose.yml   # Local Airflow 3
└── Makefile

    Config Schema¶

    config/settings.yaml¶

    Field Values Description
    solution custom Generator backend (only option)
    environment dev | staging | prod (or custom) Active environment name
    environments map of name → {class: production\|staging\|non-production, cluster: <name>} Optional custom env taxonomy; class built-in defaults used when omitted, cluster groups env names onto one Airflow deployment (e.g. dev+demo → cluster dev)
    output.mode local | image Write to directory or build Docker image
    output.local.path path Where to write .py files
    output.image.* see file Docker image name, tag, registry, push flag
    projects list of paths Optional explicit project list (auto-discovered if omitted)

    config/projects/<name>/dags.yaml¶

    name: my_project

custom_operators:
  - name: MyOp
    import_path: "plugins.my_module.MyOp"

dags:
  - id: my_dag
    schedule: "@daily"
    start_date: "2024-01-01"
    catchup: false
    tags: [example]

    enabled:          # per-environment enabled flags
      dev: true
      prod: false

    enabled_envs: [dev, staging]   # whitelist: only generated for these env names
    # OR:
    enabled_clusters: [dev]        # whitelist: only when env cluster matches (e.g. dev+demo)
    # OR:
    enabled_classes: [non-production]  # whitelist: only when env class matches

    _env:                 # DAG-level per-env overrides (schedule, catchup, max_active_runs, tags)
      prod:
        schedule: "0 4 * * *"
        max_active_runs: 2

    default_args:
      owner: my_team
      retries: 1
      retry_delay_minutes: 5
      email_on_failure: false
      _env:           # env-specific overrides
        prod:
          retries: 3

    tasks:
      - id: say_hello
        operator: BashOperator
        params:
          bash_command: "echo dev"
          _env:
            prod:
              bash_command: "echo prod"
      - id: process
        operator: PythonOperator
        enabled:
          prod: false
        params:
          python_callable: "dags.my_project.process"
        dependencies: [say_hello]

    Environment Resolution Rules¶

    1. dag.enabled_envs set and env not in list → DAG skipped entirely
    2. dag.enabled_clusters set and env cluster not in list → DAG skipped entirely
    3. dag.enabled_classes set and env class not in list → DAG skipped entirely
    4. dag.enabled[env] == false → DAG skipped entirely
    5. task.enabled[env] == false → task omitted; downstream deps cleaned up
    6. params._env[env] → merged onto base params; _env key removed
    7. default_args._env[env] → same merge applied to default_args

    Airflow 3 Features¶

    Dynamic task mapping (requires Airflow 3.0+) 

    - id: process_item
  operator: PythonOperator
  params:
    python_callable: "dags.pipeline.process"
  dynamic_map:
    expand:
      item: "{{ get_items.output }}"
    map_index_template: "item_{{ ti.map_index }}"
  dependencies: [get_items]

    Asset outlets (requires Airflow 3.0+) 

    - id: produce_data
  operator: PythonOperator
  params:
    python_callable: "dags.pipeline.produce"
  datasets:
    outlets:
      - uri: "s3://bucket/path"

    DAG display name (requires Airflow 3.2+) 

    - id: my_dag_v2
  dag_display_name: "My Pipeline (v2)"
  schedule: "@daily"
  ...

    Custom operators: 

    custom_operators:
  - name: MyOp
    import_path: "plugins.my_module.MyOp"

tasks:
  - id: run_custom
    operator: MyOp
    params:
      my_param: "value"

    Testing¶

    make test          # Go unit tests
make test-go       # same

    Pre-commit hook¶

    A hook in scripts/pre-commit automatically runs the full test suite before every git commit. Install it once:

    make install-hooks

    After installation, any commit that would break a test is blocked with a clear error. Bypass in exceptional cases with git commit --no-verify.

    Makefile Targets¶

    Target Description
    make generate Generate with env from settings.yaml
    make generate ENV=prod Override environment
    make generate ENV=prod --incremental Skip unchanged DAGs (hash cache)
    make validate Validate configs, show DAG inventory
    make build Build Go binary
    make build-go same
    make docker-build Build Docker image
    make test Go unit tests
    make install-hooks Install pre-commit hook from scripts/pre-commit
    make lint golangci-lint
    make lint-dags Check naming conventions against config/linting.yaml
    make airflow-up Start local Airflow 3
    make airflow-down Stop local Airflow
    make clean Remove generated files and build artifacts
    make promote-apply PROJECT=x FROM=staging TO=prod Print _env patch to align environments
    make check All checks: schema + operators + secrets + linting + multi-env render + docs

    Adding a New Project¶

    1. Create a directory under config/projects/<project_name>/
    2. Add a dags.yaml (or defaults.yaml + per-domain files — see config/projects/project_b/ for an example)
    3. Run make validate to confirm the config is valid
    4. Run make generate to produce the DAG files

    Custom Operators¶

    1. Copy config/plugins/my_operator.py → plugins/<your_operator>.py in your Airflow deployment
    2. Register in custom_operators in your project's dags.yaml
    3. Use the operator name in task definitions

    Generator¶

    A standalone Go binary (app/dagGen/) reads the canonical YAML, resolves environment overrides, and renders Python DAG files from text/template templates. Produces one .py file per DAG.
